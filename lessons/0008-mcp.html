B6 Týden 4 Blok B: Agentní paradigma

MCP — Model Context Protocol

Jak dát agentovi dosah k externím nástrojům a datům standardizovaným protokolem — a proč to není komplexita navíc, ale její opak

1 — Jádro

Agent umí přemýšlet o kódu, ale sám o sobě nevidí tvou databázi, nezná stav jobů na clusteru a nedosáhne na interní API. MCP — Model Context Protocol je standardizovaný způsob, jak agentovi tenhle dosah dát: připojíš MCP server, který zpřístupní nástroj nebo zdroj dat, a agent s ním umí pracovat, aniž bys psal vlastní integraci.

MCP je vrstva 4 rámce pěti otázek: „Jaký přístup k externím zdrojům agent má?" Memory je znalost, skill je postup, hook je hranice — MCP je dosah. Otevřený protokol (Anthropic, konec 2024), který standardizuje, jak agent mluví s okolním světem.

Jedno pravidlo

MCP není „další nástroj". Je to protokol — jazyk, kterým agent mluví s libovolným nástrojem. Nepiš N integrací pro N nástrojů; napiš (nebo použij) MCP server jednou a mluví s ním každý MCP klient.

2 — Problém, který MCP řeší: M×N → M+N

Bez standardu má každý AI klient (Claude Code, IDE plugin, chatbot…) vlastní způsob, jak se připojit ke každému nástroji (databáze, Git, cluster, API). M klientů × N nástrojů = M×N vlastních integrací, které někdo musí napsat a udržovat. To nefunguje — je to tatáž kombinatorická exploze, kterou historie řešila už mnohokrát.

Bez protokolu — M×N

Každý klient si píše vlastní adaptér ke každému nástroji. 5 klientů × 8 nástrojů = 40 integrací. Přidáš nástroj → 5 nových adaptérů.

roste násobně

S MCP — M+N

Každý klient mluví MCP. Každý nástroj má jeden MCP server. 5 + 8 = 13 kusů. Přidáš nástroj → jeden server, mluví s ním všichni.

roste součtově

Tohle je celé „proč MCP". Není to nová schopnost — je to standardizace rozhraní, která mění násobení na sčítání. Přesně jako USB, ovladače zařízení nebo JDBC pro databáze.

3 — Co MCP server nabízí

MCP server zpřístupňuje agentovi tři druhy věcí. Rozlišuj je — nejsou totéž:

Tools Akce, které agent může vyvolat — „spusť dotaz", „zařaď job", „vytvoř issue". Mají vedlejší efekty.
Resources Data ke čtení — obsah souboru, řádek z DB, stav jobu. Kontext, ne akce.
Prompts Předpřipravené šablony promptů, které server nabízí klientovi — opakovaný dotaz jako hotová jednotka.

Nejčastěji jde o tools (agent něco udělá) a resources (agent si něco přečte). To rozlišení má důsledek pro bezpečnost: tool s vedlejším efektem (smaže řádek) je rizikovější než resource ke čtení — a přesně tady se MCP potkává s hooky.

4 — Architektura: klient, server, transport

MCP je klient–server. Klient (Claude Code) se připojí k serveru, který zpřístupňuje nástroj. Komunikují přes definovaný transport — buď lokálně přes stdio (server běží jako proces na tvém stroji), nebo vzdáleně přes HTTP.

# .claude/settings.json — připojení MCP serverů { "mcpServers": { // lokální server jako proces (stdio transport) "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "./data"] }, // vzdálený server přes HTTP "cluster-api": { "url": "https://mcp.internal.hpc/slurm" } } }

Lokální stdio server je dobrý pro věci na tvém stroji (souborový systém, lokální DB). Vzdálený HTTP server je pro sdílené služby (interní API, cluster). Z pohledu agenta je to jedno — protokol je stejný. To je smysl standardu: agent nemusí vědět, jestli je nástroj lokální nebo za sítí.

5 — Kdy MCP (a kdy ne)

Použij MCP ✓

  • Agent potřebuje opakovaný přístup k externímu systému (DB, cluster, API)
  • Existuje hotový MCP server pro tvůj nástroj (jen ho připojíš)
  • Přístup chceš sdílet napříč klienty i lidmi v týmu
  • Integrace se bude používat dlouhodobě, ne jednou
  • Chceš standardizovaný, auditovatelný způsob přístupu

Nesahej po MCP ✗

  • Stačí jednorázově spustit příkaz → Bash
  • Je to lokální postup, ne externí zdroj → skill
  • Přidáváš server „pro jistotu", bez konkrétní potřeby
  • Řešíš tím něco, co zvládne obyčejný shell nebo soubor
  • Server by dal agentovi široký přístup, který nedokážeš ohlídat

MCP má smysl u opakovaného, standardizovaného přístupu. Na jednorázové „spusť mi tenhle skript" je MCP overkill — od toho je Bash. Otázka není „jde to přes MCP?", ale „budu tenhle přístup potřebovat opakovaně a chci ho mít standardizovaný?"

6 — Historický kontext

Standardizační protokoly, které mění M×N na M+N, jsou v inženýrství stará a osvědčená věc:

  • LSP — Language Server Protocol (Microsoft, 2016). Nejbližší analogie. Před LSP každý editor psal vlastní podporu pro každý jazyk (editorů × jazyků). LSP zavedl protokol: jeden language server na jazyk, mluví s ním každý editor. MCP je LSP pro AI nástroje.
  • ODBC / JDBC. Standardní rozhraní k databázím. Aplikace nemusí znát konkrétní DB — mluví protokolem. MCP dělá totéž pro agenty a nástroje.
  • USB. Jeden konektor místo desítek proprietárních. „USB-C pro AI" je běžná (a přesná) zkratka pro to, co MCP je.
  • Device drivers. OS nemluví s každým zařízením zvlášť — mluví s ovladačem přes standardní rozhraní. MCP server je ovladač nástroje pro agenta.

Pointa pro publikum: MCP nezavádí nový druh složitosti. Odstraňuje starý druh — kombinatorickou explozi vlastních integrací. Kdo tvrdí, že „MCP je komplikace navíc", si plete standard s tím, co standardizuje.

7 — Tři příklady

Vědec-kodér

Data má v PostgreSQL — dřív je kopíroval do CSV, aby s nimi agent mohl pracovat. Teď připojil hotový Postgres MCP server: agent se ptá přímo na schéma a čte řádky jako resources. Žádné exportování, žádné zastaralé kopie. Agent pracuje nad živými daty, ale (díky read-only serveru) je nemůže změnit — přístup ke čtení, ne k zápisu.

RSE vývojář

Tým spravuje jobs na HPC clusteru. Napsali interní MCP server nad Slurm: tools pro „zařaď job", „zjisti stav", resources pro log výstupy. Server je jeden, mluví s ním Claude Code i jejich vlastní CI bot — M+N, ne M×N. Rizikové tools (zrušení jobu) navíc jistí PreToolUse hook. MCP dává dosah, hook drží hranici.

Manažer / PI

Slyší od vývojáře „potřebuju napojit agenta na náš tracker, Jira, monitoring a DB". První instinkt: „to je čtyři projekty integrace". Realita s MCP: čtyři hotové servery se připojí konfigurací, ne kódem. MCP mění integraci z vývojového projektu na konfigurační úlohu — a standard znamená, že to, co dnes napojíte pro Claude Code, zítra použije jiný klient beze změny.

8 — Propojení na ostatní lekce

  • B2 — Rámec pěti otázek: MCP je vrstva 4 — dosah. Odpovídá na otázku „k čemu externímu agent sáhne". Nejvyšší vrstva harness před orchestací (Subagents).
  • B1 — Harness vs. Guardrails: MCP je harness — rozšiřuje, co agent umí (pozitivní architektura). Sám o sobě neomezuje. Proto se páruje s hooky.
  • B5 — Hooks: MCP dává dosah, hook drží hranici. MCP tool s vedlejším efektem (smaž řádek, zruš job) je přesně to, co má jistit PreToolUse hook. MCP bez hooků je dosah bez brzdy.
  • B4 — Skills: Skill je lokální postup; MCP je externí přístup. Skill může MCP tool volat jako krok postupu — orchestruje dosah, který MCP poskytuje.

9 — Nejčastější nepochopení

Nepochopení 1

„MCP je zbytečná komplexita — mně stačí, když agent spustí skript přes Bash."

Skutečnost

Pro jednorázové věci máš pravdu — Bash stačí. MCP se vyplatí u opakovaného, standardizovaného přístupu ke systému, který používá víc klientů nebo lidí. MCP nepřidává složitost; odstraňuje ji tím, že nahradí N ad-hoc integrací jedním protokolem. Komplexita je v tom M×N, které MCP ruší — ne v MCP.

Nepochopení 2

„MCP je bezpečnostní vrstva — když napojím databázi přes MCP, je to chráněné."

Skutečnost

MCP je dosah, ne guardrail. Dává agentovi přístup — víc přístupu, ne míň. Sám nic neblokuje. Bezpečnost přidáváš okolo: read-only server, omezená oprávnění, a PreToolUse hook na rizikové tools. MCP server s právem zápisu a bez hooku je otevřená brána, ne ochrana.

Nepochopení 3

„Musím napsat vlastní MCP server pro každý nástroj, který chci připojit."

Skutečnost

Pro běžné systémy (souborový systém, Postgres, Git, GitHub, Slack…) existují hotové MCP servery — jen je připojíš konfigurací. Vlastní server píšeš jen pro vlastní systém, který standardní server nepokrývá (interní API, váš Slurm wrapper). Napojení běžného nástroje je konfigurace, ne vývoj.

10 — Spicy teze

MCP je nejpřeceňovanější i nejpodceňovanější vrstva zároveň. Přeceňovaná lidmi, kteří po ní sahají jako po kouzelném konektoru na všechno a zavěsí si pět serverů, které nepotřebují. Podceňovaná lidmi, kteří ji odmítají jako „hype" a přitom po sté kopírují data do CSV. Není to ani zázrak, ani móda. Je to LSP pro agenty — nudná, důležitá standardizace. A nudná standardizace vždycky vyhraje nad chytrou vlastní integrací.

13 — Až se tě zeptají 🎤

Ostré dotazy z publika + krátká odpověď s pointou (tučně). Trénuj nahlas, ne čtením.

Námitka „stačí Bash": „MCP je zbytečná komplexita — mně stačí, když agent spustí skript přes Bash."

Na jednorázové věci ano. MCP se vyplatí u opakovaného standardizovaného přístupu, co používá víc klientů/lidí. MCP nepřidává složitost — odstraňuje M×N. Komplexita je v tom M×N, ne v MCP.

Nepochopení „bezpečnost": „Napojím databázi přes MCP, tak je chráněná, ne?"

MCP je dosah, ne guardrail — dává víc přístupu, ne míň; sám nic neblokuje. Bezpečnost přidáváš okolo: read-only server, omezená oprávnění, PreToolUse hook na rizikové tools. MCP se zápisem a bez hooku je otevřená brána.

Obava „vlastní server": „Musím napsat vlastní MCP server pro každý nástroj?"

Ne. Pro běžné systémy (filesystem, Postgres, Git, GitHub, Slack) existují hotové servery — jen připojíš konfigurací. Vlastní píšeš jen pro vlastní systém (interní API, váš Slurm wrapper). Napojení běžného nástroje je konfigurace, ne vývoj.

Otázka „tools vs. resources": „Jaký je rozdíl mezi tools a resources?"

Tools = akce s vedlejším efektem (spusť dotaz, zařaď job) — rizikovější. Resources = data ke čtení (obsah, řádek DB, stav jobu) — kontext, ne akce. Rozdíl má důsledek pro bezpečnost: rizikový tool jistíš hookem.

Otázka „co to vlastně řeší": „Řekni MCP jednou větou — co řeší?"

Kombinatorickou explozi integrací: M klientů × N nástrojů → M+N. Standardní protokol místo N ad-hoc adaptérů. Je to LSP (nebo USB-C) pro agenty.

Otázka „lokální vs. vzdálený": „Je rozdíl, jestli server běží lokálně, nebo na síti?"

Pro agenta žádný. Lokální (stdio, proces na tvém stroji) i vzdálený (HTTP, sdílená služba) mluví stejným protokolem. Agent nemusí vědět, jestli je nástroj lokální nebo za sítí — to je smysl standardu.

16 — Co dál

Co musíš znát před touto lekcí:

  • B2 — Rámec pěti otázek — MCP je vrstva 4. Tato lekce ji rozvíjí do detailu.
  • B5 — Hooks — MCP dává dosah, hook drží hranici. Rizikové MCP tools bez hooku jsou brána bez brzdy.

Praktický úkol (25 minut): Vyber externí systém, se kterým teď pracuješ ručně (databáze, Git, souborový systém). Najdi hotový MCP server (většina běžných existuje) a připoj ho v settings.json. Dej agentovi úkol, který dřív vyžadoval kopírování dat ven — a pozoruj, že teď sáhne rovnou ke zdroji. Pak si rozmysli: který tool tohoto serveru by měl jistit hook?

Příští lekce:

  • Subagents (vrstva 5) — poslední vrstva rámce pěti otázek: orchestrace. Jak jeden agent řídí víc podřízených agentů pro paralelní nebo izolovanou práci (např. review bezpečnosti vs. správnosti zvlášť). Memory, Skills, Hooks a MCP jsou stavební kameny — Subagents je skládají do postupu.

Propojení do curricula:

  • C1 — FAIR4RS — MCP může standardizovat přístup k datovým repozitářům a metadatům; FAIR přístupnost (A) má v MCP praktický nástroj.
  • A5 — Agile Manifesto — „fungující software nad dokumentací": MCP je fungující standard, ne specifikační dokument. Přijali ho, protože řeší reálný M×N problém, ne protože je hezky navržený.
